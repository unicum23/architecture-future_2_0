# Задание 1. Узкие места и расстановка приоритетов

## 1. Узкие места текущего ландшафта (as-is)

| № | Узкое место | Описание | Затронутые бизнес-сценарии |
|---|-------------|----------|----------------------------|
| P1 | Монолитный DWH (SQL Server 2008) как «центр притяжения» | Бизнес-логика и отчётность сосредоточены в одном хранилище; объём — сотни ТБ; устаревшая СУБД | Оперативная отчётность; управленческие решения; планирование инвестиций и развития филиальной сети |
| P2 | Длительное формирование сложных отчётов (часы) | Интенсивные трансформации «на лету», конкурирующая нагрузка с операционными процессами | Оперативное управление; реакция на изменения рынка; соблюдение регуляторных сроков |
| P3 | ESB (Apache Camel) как узкое место интеграционного слоя | Синхронные цепочки вызовов, высокая стоимость сопровождения, риск деградации при росте трафика; концентрация ФЛК, трансформаций и бизнес-логики в монолитных маршрутах | Независимый релиз функций финтеха и ИИ; подключение новых партнёров (фарма, оборудование); время реакции на отказы |
| P4 | Разрозненные потоки медицинских данных (DWH ↔ оператор vs ESB ↔ ИИ) | Дублирование данных, рассинхронизация, сложность построения целостной картины в рамках разрешённых срезов | Качество клинического сервиса в части согласованности данных; затраты на межкомандную сверку |
| P5 | BI поверх DWH с глубокой кастомизацией | Тяжёлые прямые запросы к DWH, хрупкость при изменениях схемы | Стабильность корпоративной отчётности; скорость адаптации KPI при появлении новых продуктов |
| P6 | Риски ИБ и комплаенса на устаревшем контуре | Legacy-стек, затруднённость аудита и геораспределения | Финансовые сервисы (банковская лицензия); работа с конфиденциальными данными |
| P7 | Перенос новой бизнес-логики в DWH по инерции | Замедление time-to-market новых доменов | Выход на новые рынки; выручка от новых продуктовых линеек |

## 2. Приоритизация: матрица Эйзенхауэра

Оси: **срочность / влияние на бизнес-цели** (выручка, time-to-market, качество медицинских и финансовых сервисов).

| Квадрант | Проблемы | Связь с бизнесом |
|----------|----------|-----------------|
| **Сделать немедленно** (срочно + важно) | P2, P6 | Неприемлемое время построения отчётности блокирует управленческие решения; несоответствие требованиям ИБ/комплаенса создаёт недопустимые регуляторные риски для банковского и медицинского контуров. |
| **Запланировать** (не срочно + важно) | P1, P3, P5, P7 | Стратегически определяют выручку и TTM через платформу данных и доменную автономию; эффект проявляется через кварталы, однако без закладки этих изменений сейчас целевое состояние через год недостижимо. |
| **Делегировать / сократить** (срочно + менее важно) | P4 | Существенно для согласованности данных, но частично решаемо через контракты данных и инкрементальную синхронизацию без блокировки первого релиза витрины. |
| **Не делать сейчас / минимизировать** (не срочно + не критично в первую очередь) | — | Все перечисленные проблемы значимы; в «хвосте» — точечная оптимизация отдельных отчётов, не меняющая архитектуры. |

## 3. Приоритизация: MoSCoW

Привязка к целям: **выручка и новые продукты**, **скорость выхода на рынок**, **качество финансовых и медицинских сервисов**, **масштабирование под новые бизнесы**.

| Приоритет | Проблемы / направления | Комментарий |
|-----------|------------------------|-------------|
| **Must have** | Сократить время получения ключевой отчётности (P2) через витрины и семантический слой; обеспечить ИБ и аудит на целевом контуре (P6); исключить попадание сырых медкарт в витрину (ограничение scope — из условий задачи) | Без этого бизнес не получает обещанный портал самообслуживания, а регуляторные риски становятся неприемлемыми. |
| **Should have** | Разгрузить монолитный DWH (P1) через lakehouse и мост; рефакторинг ESB (P3) — вынос функций в целевые компоненты; перевести BI на семантический слой (P5); ограничить вынос новой логики в DWH (P7) | Напрямую влияет на TTM и стоимость владения данными. |
| **Could have** | Повысить согласованность медицинских потоков данных (P4) в части сценариев, не нарушающих доменные границы | Улучшает качество ИИ-сценариев и клинических процессов; реализуется итерационно. |
| **Won't (в горизонте первого года)** | Полный отказ от legacy без переходного моста; замена ESB единовременным «большим взрывом» без поэтапной миграции на события и API | Сохранение переходного legacy допускается по условиям задачи; полная замена — за горизонтом первого года. |

## 4. Миграция логики ESB в целевую архитектуру

Текущий ESB (Apache Camel) является монолитом интеграционного слоя, концентрирующим несколько разнородных ответственностей. В целевой архитектуре каждая функция мигрирует в профильный компонент:

| Функция ESB | Целевой компонент | Обоснование |
|---|---|---|
| **ФЛК** (форматно-логический контроль входящих сообщений) | Schema Registry (Kafka) + контракты данных | Декларативная валидация на уровне схем (Avro/Protobuf) — контракт между продюсером и консюмером, не требует кода маршрута |
| **Адресация / content-based routing** | API Gateway (синхронные вызовы) + Kafka топики (асинхронные потоки) | Синхронный routing по правилам — зона ответственности шлюза; доменное разделение потоков — через выделенные топики |
| **Трансформация и маппинг форматов** (операционные потоки) | Integration & Orchestration Layer | Сохраняет функцию трансформации, но в явно выделенном, тестируемом и масштабируемом сервисе; не смешивается с доменной логикой |
| **Трансформация** (аналитические потоки, ETL в DWH) | Ingestion Layer (dbt, Airflow, cloud ETL) | Аналитические трансформации отделены от операционных; версионируются как код (dbt-модели) |
| **Бизнес-оркестрация** (многошаговые межсистемные сценарии, saga) | Integration & Orchestration Layer (Temporal / Conductor / рефакторинг Camel) | Явная модель состояния процесса; retry, compensation, observability — не скрыты в XML-маршрутах |
| **Доменная бизнес-логика** (ранее вшитая в ESB-маршруты) | Соответствующие доменные сервисы (финтех, клиники) | Логика, принадлежащая домену, возвращается в домен; ESB не должен владеть доменными правилами |
| **Интеграция с внешними партнёрами** (фарма, оборудование) | B2B Integration Gateway | Изолирует нестандартные протоколы и форматы партнёров; внутренний ландшафт не зависит от специфики внешних контрагентов |

**Ключевой принцип:** Integration & Orchestration Layer — не новый ESB. Его ответственность ограничена **транзитными интеграционными сценариями**: оркестрация, трансформация форматов между системами, обработка ошибок с компенсацией. Он не владеет доменными данными и не содержит доменных правил.

## 5. Сводная последовательность (связь методов)

1. **Эйзенхауэр:** фокус текущего квартала — время отчётности и комплаенс (P2, P6); параллельно стартуют архитектурные работы по P1, P3, P5, P7.
2. **MoSCoW:** must — витрина + безопасность + границы данных; should — аналитическая платформа, рефакторинг ESB, вынос доменной логики из DWH; could — выравнивание потоков медицинских данных; won't на год — полный снос legacy без эволюционной миграции.
