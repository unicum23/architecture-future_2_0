# Обоснование конфигурации Terraform

## 1. Выбор облака и провайдера

Используется **Yandex Cloud** и официальный провайдер `yandex-cloud/yandex`: он описывает те же IaaS-сущности, что и консоль (сети, подсети, NAT, группы безопасности, диски, виртуальные машины), что соответствует заданию на проектирование облачной инфраструктуры с **IaaS** и автоматизацией через **Terraform 1.x**.

Аутентификация: переменная окружения **`YC_TOKEN`** (OAuth-токен, полученный через `yc iam create-token` или веб-консоль). Токен не хранится в `.tf`-файлах.

## 2. Сетевая модель и NAT

- **VPC** (`yandex_vpc_network`) — изолированная сеть для пилота.
- **Публичная подсеть** `10.10.0.0/24` — размещение **bastion** с включённым **NAT на сетевом интерфейсе ВМ** (`nat = true`), чтобы обеспечить фиксированный публичный IP для входящего SSH.
- **Приватная подсеть** `10.10.1.0/24` — размещение прикладной ВМ **без** публичного IP; исходящий трафик в интернет направляется через **NAT-шлюз** Yandex Cloud (`yandex_vpc_gateway` с `shared_egress_gateway`) и **таблицу маршрутов** с маршрутом `0.0.0.0/0` на этот шлюз. Таким образом выполняется требование задания по **настройке NAT** при типичной схеме «приватные ВМ + контролируемый выход в интернет».

Такое разделение сокращает поверхность атаки: прикладная ВМ недоступна из интернета напрямую; доступ — по SSH через bastion.

## 3. Размеры ВМ и дисков

| Ресурс | Параметры по умолчанию | Обоснование |
|--------|------------------------|-------------|
| **Bastion** | `standard-v3`, 2 vCPU, 2 ГБ RAM, диск 10 ГБ SSD | Минимально достаточная конфигурация для SSH-перехода; `core_fraction = 20` снижает стоимость. |
| **App** | `standard-v3`, 4 vCPU, 8 ГБ RAM, загрузочный диск 20 ГБ SSD | Базовый рабочий размер под приложение / агент в пилоте; `core_fraction = 100` обеспечивает стабильную производительность. |
| **Данные** | Отдельный диск `network-hdd`, 50 ГБ | Демонстрация отдельного управляемого диска (съёмный том, резервное копирование по политикам облака); HDD дешевле для холодных данных. |

Размеры вынесены в **variables** и `terraform.tfvars`, чтобы масштабировать среду под нагрузочные тесты или оптимизацию затрат без правки кода.

## 4. Группы безопасности

- На **bastion** разрешён входящий **SSH (22)** только с CIDR из переменной `admin_cidr` (рекомендуется ограничить своим публичным IP `/32`).
- На **app** разрешён SSH исключительно из CIDR **публичной** подсети (где расположен bastion), а не из всего интернета.

Исходящий трафик разрешён (для обновления пакетов и работы через NAT).

## 5. Декларативный подход (Terraform)

Конфигурация описывает **желаемое состояние** (какие ресурсы и с какими параметрами должны существовать), а провайдер вычисляет расхождение с облаком и создаёт / изменяет ресурсы. Это обеспечивает:

- предсказуемые повторяемые прогоны (`plan` перед `apply`);
- версионируемое описание инфраструктуры в Git;
- минимизацию ручных ошибок при работе в консоли.

## 6. Infrastructure as Code и воспроизводимость

IaC позволяет:

- **воспроизвести** стенд в другом каталоге или облаке, изменив `folder_id` / `cloud_id` и значения в `tfvars`;
- **масштабировать** вертикально (через переменные `*_resources`, `data_disk_size`) и горизонтально (добавление новых `yandex_compute_instance` по шаблону);
- передавать конфигурацию команде и проводить ревью изменений так же, как кода приложения.

State-файл (`terraform.tfstate`) хранит соответствие имён и ID в облаке; для командной работы рекомендуется удалённый бэкенд (Object Storage и др.) — в учебном задании достаточно локального state при условии, что он не попадает в публичный репозиторий.

## 7. Что создаётся вручную

Отражено на **manual-diagram**: организационные и разовые действия вне Terraform (создание облака / каталога, биллинг, выпуск токена, при необходимости квоты и внешний DNS). Они не дублируются в `.tf`, чтобы не смешивать учётные и организационные шаги с описанием ресурсов каталога.

Токен должен быть задан в том же сеансе терминала, что и `terraform`, иначе переменная недоступна процессу.
